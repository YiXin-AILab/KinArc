# Changelog

维护指定的一份累计日志。每轮只建一个版本组，包含两个版本：

- **评测版本**：本轮代码和 Train 结果所属版本。
- **迭代版本**：本轮修改后准备交付的版本，发布后才成为正式 Candidate。

日志随版本继承。本轮记录实际修改，下一轮根据最新 Train 证据补齐相关 Case 的效果。
新版本组用 write_file 的 prepend 一次插入文件最前面，并与旧日志留空行；
已有版本组按 ID 使用 replace 原位修改，不移动历史版本组，不倒置组内章节。

## 平台恢复版本

平台恢复组由平台生成，没有 CASE 待填标记。其 Train/Validation 证据来自恢复来源，
不是重新执行；Train 与父级的分数差也不证明某项业务修改的因果效果。
遇到恢复版本直接进入本轮诊断，不为恢复动作补写业务 diff、修改解释或 CASE 结果。
latest 模式保留的被撤回版本待填标记可以保持原样，不用恢复版本证据回填。
best 模式只继承最佳版本日志，不要求补回被丢弃的探索日志。

## 1. 回填上轮结果

1. 找到“迭代版本”等于本轮“评测版本”的版本组，核对其中的修改和关联 Case。
2. 按需读取最新 Train 反馈和轨迹，将待结果标记替换为相关 Case 的实际效果：
   分数及可比的变化、实际行为、原问题是否解决、是否退化，以及效果判断的依据。
   缺少旧分数不推断分数变化，证据不足记为“未确认”。
3. 无唯一匹配组时不猜测归属；没有待结果标记仍须复盘。
   已有结果不覆盖，新证据修正旧判断时，在本轮“变更依据”中引用原版本追加说明。

用 write_file 的 replace、replace_all=false 精确替换唯一标记，再回读确认。
标记缺失或重复时说明问题，不猜测或批量替换。

## 2. 记录本轮修改

比较本轮结束时与开始时的 Target，记录最终留下的修改：

- 有净变化：使用下方模板，多项修改分别记录五个问题章节。
- 某项没有净变化：说明原因，该项“相关CASE测试结果”写“不适用”，不留标记。
- 整个 Target 没有净变化：记录 NO_CHANGE 及原因，本轮各结果节写“不适用”，不留标记。

Agent 自行撤回上轮已发布改动会产生新的 diff，需要评测；本轮尝试后恢复原样才没有净变化。
平台恢复已复制评测证据，不适用这条重新评测规则。
仅日志变化不会单独发布。每次进化只能有一组“评测版本 / 迭代版本”标题；已有就补充，禁止重复追加。
“问题类型、问题Case、文件变更、变更依据、相关CASE测试结果”可按修改项重复多次。
本轮记录到最后一项“相关CASE测试结果”为止。
每项修改必须在“问题类型”中声明：目标失败簇（诊断简报的 cluster_id，无具体簇时写“无具体簇”）、机制族（prompt_instruction / skill_procedure / tool_configuration / config_tuning / middleware_instruction 五选一）、保护的通过 case（本轮改动不得影响的通过 case ID，或“无关联”）。
NO_CHANGE 需写明弃权原因，并逐个说明诊断简报中的可处理失败簇为何跳过（无安全可复用的修改、证据不足等）；“问题库（单 case 簇积累中，本轮不处理）”列出的簇由平台延后处理，不属于可处理簇，不需要跳过理由。

```markdown
## 评测版本：<本轮评测版本ID>
## 迭代版本：<本轮迭代版本ID>

### 问题类型
要解决的问题；未证实的原因标为假设。
目标失败簇：<诊断简报中的 cluster_id 或“无具体簇”>
机制族：<prompt_instruction / skill_procedure / tool_configuration / config_tuning / middleware_instruction 之一>
保护的通过 case：<本轮改动不得影响的通过 case ID，或“无关联”>

### 问题Case
关联的训练 Case ID；没有具体 Case 时写“无具体 Case”。

### 文件变更
相对评测版本的最终 diff。完整展示实际增删，新增文件展示全文，不能用概述代替 diff。
保留的未改内容不算新修改。

### 变更依据
修改依据、预期行为、可证伪条件及需要保留的正确行为；假设与事实分开。
已被证据否定的方案没有新证据时不得原样重试。
修正历史判断时，引用原版本并说明新证据。

### 相关CASE测试结果
CHANGE_RESULT_<本轮迭代版本ID>_<唯一随机后缀>
```

“相关CASE测试结果”记录这项修改之后的 Case 效果，本轮尚未评测，只填写待回填标记。
CHANGE_RESULT 标记使用本组迭代版本 ID，每项修改使用不同的唯一后缀。
下一轮按“迭代版本 = 本轮评测版本”找到对应版本组，回填其中各项结果。
版本标题和标记中的 ID 保持创建时的值。

提交前回读日志，确认 diff、Case、依据对应，每个待回填标记在整份日志中只出现一次，历史内容完整；
每项修改已声明目标失败簇、机制族和保护的通过 case；NO_CHANGE 已写明弃权原因及跳过各可处理失败簇的理由。
写入失败如实说明。

## 3. 下一轮复盘

下一轮将这个版本作为“评测版本”，从第 1 步开始，回填关联 Case 的实际效果。
总分变化不能代替单项修改的效果分析，文件已修改也不代表问题已解决。
