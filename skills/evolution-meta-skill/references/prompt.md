# Prompt

## 优化策略

基于评测证据改进提示词的整体设计，使目标 Agent 更稳定地完成同类任务。
修改幅度由问题决定：可以澄清一句规则，也可以重构整个提示词。

### 1. 理解任务与现有设计

结合任务要求、现有提示词和可用能力，明确 Agent 要完成什么、依据什么信息、
能执行哪些操作，以及怎样才算完成。理清当前提示词如何组织这些内容，
识别必须保留的业务要求与已有正确行为，不能只围绕失败片段改写。

### 2. 从失败中提炼设计问题

沿“当时可见的信息 → 实际决策或操作 → 结果”定位偏差，提出可验证的原因假设。
区分目标不清、信息缺失、判断含糊、流程遗漏、规则冲突和执行能力不足。
同类失败可共同支持一个问题；相似表象不应强行归为同一原因。

明确此次修改预计改变哪次决策。业务规则依据任务要求、业务文档和工具契约；
expected 用于定位差异，不能单独产生默认值或通用规则。
若原因在信息来源或执行能力，转到对应组件解决。

### 3. 选择方法并完成改写

按问题选择或组合方法，不必全部使用。

| 设计问题 | 优化方法 | 如何改写 |
| --- | --- | --- |
| 目标模糊、职责混杂、内容重复或冲突 | 结构化重写 | 提取任务目标、决策规则、行动边界与完成条件；合并同义内容，依据任务要求消解冲突，再按执行时需要的信息顺序组织。结构服务于任务，不套用空泛角色模板 |
| 多步骤任务漏项、顺序错误或提前结束 | 流程设计 | 围绕完成目标拆分阶段，为每阶段明确输入、动作、完成依据及失败后的去向；有依赖才规定顺序，独立事项保留灵活性 |
| 抽象要求无法执行、条件或例外含糊 | 决策规则设计 | 将要求改写为“条件 → 行动 → 判断依据”，给出信息不足时的处理方式；将例外紧邻对应规则，独立属性分别判断 |
| 规则已清楚但相近概念仍被混淆 | 对比示例 | 选择仅关键条件不同的一组情境，展示不同的正确行动并点明区别；使用通用情境，去除评测题目的身份、数值等无关细节 |
| 大量细节遮蔽全局决策 | 信息分层 | 保留始终需要的目标、边界与决策原则，将专项流程组织到 [Skill](skills.md)，将工具局部约束放入 [工具描述或 rules](tools.md)，明确按需获取信息的时机 |

例如，将“确保信息完整”改成：
“复用已获得的有效信息；缺少会影响当前决策的必要信息时，先查询可用来源，仍缺失再澄清。”
这样既说明如何补齐信息，也避免每次重复询问。

区分“受理”与“完成”时，可用对比示例：
“收到请求回执 → 报告已受理；收到明确完成结果 → 报告已完成。”
示例应与真实工具契约一致。

### 4. 检查整体行为

把修改融入相关段落，替换失效规则并清理重复表述。通读完整提示词，
检查目标、流程、约束和完成条件是否一致，新增要求是否有可用信息与工具支持。

以目标失败场景、相近正确场景和规则不适用的边界场景推演执行过程，
检查是否引入多余澄清、错误默认值、漏调工具或提前结束。
局部规则正确，不代表整个任务流程仍然合理。

### 5. 根据反馈修订设计

在现有 Changelog 中说明：设计问题与证据、采用的方法、预期行为变化及应保留的正确行为。
下一轮核对预期行为是否出现、目标错误是否解决，以及其他行为是否退化。
根据证据保留、修订或撤回方案；未找到关联时保留未知，不靠追加例外维护原方案。
静态推演不等于实际效果，总分变化也不能单独证明因果。

## 优化质量控制

修改前检查完整提示词，交付前检查全文与 diff。不要把上一轮留下的内容默认视为必要。

### 控制累积膨胀

用同一口径统计字符数或 token 数，并结合可用历史检查累计增长。
篇幅增长却没有对应的新任务要求，或同一决策散落在多处、反复追加 case 和例外时，
停止追加规则，先整理已有内容；不能仅以“每条都有用”解释继续增长。

对已经膨胀的提示词，按以下顺序重构：

1. **提取要求**：从全文提取独立的业务要求、决策条件、行动、例外与完成标准，
   区分有依据的要求和历轮补丁；历史解释、重复强调与案例答案不自动成为要求。
2. **归并决策**：将影响同一决策的内容合为一条规则及其必要分支；
   按业务依据消解冲突，删除失效补丁，仅保留能区分易混决策的示例。
3. **替换全文**：依据归并后的要求重新组织提示词，移除被替代的旧段落，
   不保留“原文 + 精简版”。专项细节按需移入 Skill 时，确认启用与读取时机，避免只搬走问题。
4. **核对覆盖**：逐项确认有效要求在新版本中的去向；删除须有重复、失效或无依据等理由。
   用原失败场景、相近正确场景和例外场景检查决策，不能靠丢失条件换取缩短。

治理膨胀须同时做到：移除重复与失效内容、保留有效要求、减少篇幅。
若独立且必要的要求本身就很多，应调整信息分层，不强行压缩到任意字数。
在现有 Changelog 中记录前后长度、主要归并或删除项及未验证的行为；效果仍由评测验证。

### 修正其他退化

| 风险信号 | 修正动作 |
| --- | --- |
| 默认值、固定顺序或例外仅来自某道评测题 | 删除无独立业务依据的特例，恢复依据当前信息判断的规则 |
| 修复失败后，正常场景出现无关查询、重复确认或不必要拒绝 | 收窄规则触发条件，检查适用与不适用场景，保留原有正确行为 |
| 新要求改变任务边界，或依赖不存在的信息与工具 | 恢复有依据的目标与完成标准，将信息或能力缺口交由对应组件处理 |
| 多轮改写同一规则仍无改善 | 检查实际 trace 中规则是否可见、是否执行及失败原因，撤回无效补丁，重新选择优化方式；不要继续加强措辞 |

## 系统修改说明

修改目标 Agent 配置中 `prompt` 指向的文件；更换文件时同步更新路径。

| 项目 | 说明 |
| --- | --- |
| 配置入口 | `AgentConfig.prompt` 为必填非空路径，标准加载器限制在应用根内 |
| Markdown | `.md` 按 UTF-8 读取全文，去除首尾空白后内容不能为空 |
| 上下文组合 | Runtime 将基础提示词、工具规则和 Skill 目录组合为 SYSTEM；Skill 正文按需读取，工具 schema 单独传递 |
| 生效方式 | 修改后重新加载 Agent，并在新 Session 中验证；已有 Session 的 SYSTEM 不随文件更新 |

基础 Prompt 按原文组合；默认 safety 分区为空。
宿主提供可用 MemoryService 时，首次 SYSTEM 按启用作用域渲染完整记忆快照，
该快照在 Session 内保持不变；启用条件见 [配置](agent-config.md#内置能力配置)。
需要完整替换 SYSTEM 时，可通过 before_system_prompt_build / after_system_prompt_build
Middleware 返回 update；before 替换会跳过默认分区和 Memory 读取，after 仍执行。
挂点的 payload 与初始化失败语义见 [Middleware](middlewares.md)。
